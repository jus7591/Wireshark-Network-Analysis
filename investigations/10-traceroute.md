# Traceroute Investigation

## Objective

Analyze how the Windows `tracert` utility discovers the path between a local computer and a remote destination.

The investigation focuses on IPv6 traceroute traffic, including ICMPv6 Echo Requests, IPv6 Hop Limits, ICMPv6 Time Exceeded messages, response times, and non-responsive hops.

The goal is to understand how traceroute can be used as a practical network troubleshooting tool rather than simply viewing it as a list of routers.

## How Traceroute Works

Traceroute determines the path to a destination by manipulating the IPv6 **Hop Limit** field.

The Hop Limit is decremented by each router that forwards an IPv6 packet.

When the Hop Limit reaches zero, the router discards the packet and normally generates an ICMPv6 **Time Exceeded** message.

Traceroute uses this behavior to identify intermediate routers.

The process can be represented as:

```text
Computer
   |
   | Hop Limit = 1
   v
Router 1
   |
   | Hop Limit reaches 0
   v
ICMPv6 Time Exceeded
   |
   v
Computer
```

Traceroute then increases the Hop Limit:

```text
Hop Limit = 1 → Discover first responding router
Hop Limit = 2 → Discover second responding router
Hop Limit = 3 → Discover third responding router
...
```

This process continues until the destination responds.

## Wireshark Packet Analysis

Wireshark was used to examine the packets generated during the traceroute.

The capture showed that the traceroute was using **ICMPv6**.

The original traceroute probe contained:

```text
Next Header: ICMPv6 (58)
Hop Limit: 1
ICMPv6 Type: Echo (ping) request (128)
```

The destination was the IPv6 address associated with the Google destination.

The Hop Limit of `1` is significant because the first responding router that receives the packet will decrement the value to zero.

---

## ICMPv6 Time Exceeded Response

The capture also contained an ICMPv6 Time Exceeded message.

The relevant fields were:

```text
Type: Time Exceeded (3)
Code: 0 (Hop limit exceeded in transit)
```

This confirms that the router discarded the traceroute probe because its Hop Limit had expired.

The ICMPv6 error message also contained information from the original Echo Request that caused the error.

This allowed the original traceroute probe to be correlated with the router's response.

## Correlating Wireshark With Traceroute

The ICMPv6 Time Exceeded packet was generated by the router represented by Hop 2 in the traceroute output.

The command-line results showed:

```text
Hop 2: 1 ms, 1 ms, <1 ms
```

The corresponding Wireshark packet showed:

```text
ICMPv6 Type: Time Exceeded
Code: 0
```

The encapsulated original IPv6 packet showed:

```text
Hop Limit: 1
ICMPv6 Type: Echo Request
```

This provides direct evidence of the traceroute process:

```text
ICMPv6 Echo Request
        |
        | Hop Limit = 1
        v
     Router
        |
        | Hop Limit → 0
        v
Packet discarded
        |
        | ICMPv6 Time Exceeded
        v
   Local Computer
```

The router's response allowed `tracert` to identify that router as a hop in the path.

## Response Times

Each hop normally displayed three response-time measurements.

For example:

```text
Hop 3:
3 ms
3 ms
3 ms
```

Sending multiple probes provides several measurements for the same hop.

The results also demonstrated that latency does not necessarily increase at every individual hop.

For example, some later hops had slightly lower response times than previous hops.

This is normal because network latency can vary based on routing, queuing, processing, and how individual routers handle traceroute probes.

---

## Non-Responsive Hops

Several hops did not respond to the traceroute probes.

The first hop showed:

```text
* * *
Request timed out.
```

Hops 12 through 21 also showed timeouts.

However, the destination eventually responded at Hop 22:

```text
24 ms
24 ms
23 ms
```

This is an important troubleshooting observation.

A timeout at an intermediate hop does **not automatically indicate a network failure**.

Routers can be configured to ignore, filter, rate-limit, or deprioritize traceroute-related responses while continuing to forward normal traffic.

The fact that later hops and the final destination responded demonstrates why a `*` entry should not automatically be interpreted as a broken router.

---

## Important Troubleshooting Observation

The traceroute results demonstrated this pattern:

```text
Hop 11
   |
   v
Hop 12 *
   |
Hop 13 *
   |
Hop 14 *
   |
...
   |
Hop 21 *
   |
   v
Hop 22 — Destination responds
```

If Hop 12 were interpreted as a complete network failure simply because it did not respond, the investigation could lead to an incorrect conclusion.

Instead, the entire path must be considered.

Because the destination ultimately responded successfully, the non-responsive hops were not sufficient evidence by themselves to identify a connectivity failure.

## What I Learned

This investigation helped me understand how traceroute actually discovers network paths instead of treating it as simply a command that lists routers.

I learned that IPv6 uses a **Hop Limit** field that functions similarly to the IPv4 TTL field. Traceroute intentionally sends probes with a low Hop Limit so that intermediate routers eventually discard the packets and return ICMPv6 Time Exceeded messages.

Using Wireshark, I was able to see this process directly.

The capture showed an ICMPv6 Echo Request with a Hop Limit of `1`. The corresponding response was an ICMPv6 Time Exceeded message with Code `0`, indicating that the Hop Limit had been exceeded in transit.

I also learned that traceroute timeouts need to be interpreted carefully. A router that does not respond to a traceroute probe can still successfully forward traffic. In this investigation, multiple consecutive hops timed out, but the destination eventually responded successfully.

This reinforced an important troubleshooting principle: **a lack of response from an intermediate device does not automatically mean that device is the source of a network problem.**

## Real-World Troubleshooting Applications

Traceroute can be useful when investigating problems such as:

* High latency to a specific destination
* Intermittent connectivity
* Routing problems
* Unexpected network paths
* Potential upstream ISP issues
* Determining whether a destination is reachable
* Identifying where latency begins to increase significantly

A basic troubleshooting process could be:

1. Verify the local device has valid network configuration.
2. Test connectivity to the local gateway.
3. Verify DNS resolution.
4. Run `tracert` to the affected destination.
5. Compare response times across the hops.
6. Look for where latency changes significantly.
7. Determine whether intermediate devices are responding.
8. Check whether the final destination is reachable.
9. Avoid assuming that a timeout automatically represents a failed router.
10. Use packet capture or additional testing when traceroute alone is inconclusive.

Traceroute is therefore best treated as **one troubleshooting tool among several**, rather than definitive proof of where a network problem exists.

## Conclusion

The traceroute investigation demonstrated how Windows uses ICMPv6 Echo Requests and the IPv6 Hop Limit to discover the path to a remote destination.

Wireshark provided packet-level evidence of the process by showing an Echo Request with a Hop Limit of `1`, followed by an ICMPv6 Time Exceeded response when the Hop Limit expired.

The investigation also demonstrated an important troubleshooting concept: intermediate routers may not respond to traceroute while continuing to forward traffic normally.

By combining the `tracert` output with Wireshark packet analysis, the investigation connected the command-line results to the underlying network protocols and demonstrated how traceroute can be used as a practical network troubleshooting tool.
